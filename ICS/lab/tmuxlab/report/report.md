## 1. 实现功能与测试结果

我根据自建的盲测结果和各轮autograde的结果总结一下我实现的所有功能。

### 1.1 基础功能

- client 与 server 架构：server 常驻维护状态，client 连接后负责交互显示与输入。
- Unix domain socket 通信：client 通过 hello/attach 等流程连接到 server。
- PTY + shell 子进程：每个会话/窗格背后是真正的 PTY，shell 在 slave 端运行，保证终端语义一致。
- 多 session：不同 session 之间的进程组与信号隔离。
- 多 client attach：多个 client 可以同时 attach 同一 session。
- readonly attach：只读 client 不允许发送输入，保证运行环境的稳定性。
- detach/reattach：client 断开后，server 仍维持会话与子进程，后续可重新连接。
- SIGCHLD 回收：子进程退出后能正确 waitpid，避免僵尸进程。

### 1.2 Bonus 功能

- 多 pane：支持创建 pane、切换焦点、杀死 pane。
- 布局与 resize：pane 数量变化或 client 尺寸变化后会重新计算布局，并对各 pane 下发正确的 winsize，同时传播 SIGWINCH。
- 日志输出（:log / :log-stop）：把指定 pane 的输出写入文件，并可停止。
- 管道输出（:pipeout / :pipeout-stop）：把指定 pane 的输出 pipe 到外部命令。
- 屏幕捕获（:capture）：把 pane 当前内容/输出保存到文件，用于测试与回归验证。

## 2. 我对这个 lab 的浅薄理解

身为一个人类，我能读懂的部分仅限于部分基础功能的说明，所有的 bonus 功能对我来说已经是天书了，因此我需要结合 AI 来理解整个系统的构成。以下是我对两个模块的具体认知：

### 1. PTY 和控制终端的结合

如果不使用一对 master/slave 设备，而是直接用普通的 pipe 管道，很多需要交互的程序根本运行不了。比如探针（probe）会调用 `isatty()` 检查，发现是普通管道就会返回 false，程序因此判断没有交互终端，直接报错退出了。

观察代码后发现程序具体是这么做的：首先让 server 调用 `openpty()` 创建一对 master 和 slave，并把窗口大小 winsize 提前设置好。然后 `fork()` 出子进程，在子进程里必须有一句关键的 `setsid()` 来创建一个新的会话，紧接着用 `ioctl(slave, TIOCSCTTY, 0)` 把这个 PTY slave 直接设置成子进程的控制终端。为了保证按键发出的信号不串台，程序还用 `tcsetpgrp(slave, getpid())` 把前台进程组锁定到了子进程自己身上。最后再用老套路 `dup2()` 把 slave 复制给 0, 1, 2，然后 `exec` 启动 shell。

这么一连串设置带来的直接效果就是，每个 pane 里的 shell 都觉得自己在一个真正的屏幕面前跑着。当我在某个 pane 里按下 `Ctrl+C` 的时候，只有这个 pane 的前台进程组会收到 SIGINT 信号，所以其它 session 是完全不受打扰的。

### 2. Detach 和 Reattach
Detach 并不是关掉 shell，而是只断开当前的 client 进程，后台的 server 和各个 pane 里的子进程还得接着跑。

在程序的实现中，server 的 `poll` 每次从 pane 的 PTY master 读到新输出，除了要把数据广播给还在的 client 外，还会把这批输出塞进一个叫 `replay_history` 的存储结构里（代码里限定了它的最大缓存容量防爆内存）。然后，一旦有新 client 通过 socket 发送 hello 并连上来，server 就会把当前焦点 pane 缓存在 `replay_history` 里的这波历史字节流，直接封装成 output 帧主动发过去。

正是靠着这一套缓存与回放机制，新连上的 client 一进门就能立马看见之前的上下文。

## 3. 如何和 AI 协作完成整个 lab

本实验中我使用的 AI 为 GitHub Copilot（GPT 5.3 Codex），大概花费了不到 5% 的高级额度便完成了基础和 Bonus 功能的实现，这其中还包含了我自建脚本的 prompt 以及生成报告大纲的 prompt。看到这样一个数字不得不感叹一句现在的 AI 实在是太猛了，相当于我出了一点点力就把这么庞大一个 lab 给做完了。与 copilot 的对话记录我保存在了 `\report` 文件夹中,下面是一些概括性的文字描述。

### 3.1 基础功能

由于实验提供了公开的测试点供我检验功能的实现情况，我便直接让 copilot 定位说明文档的基础功能部分，逐个实现，统一测试，将“Failed"的测试点修复，直到所有的公开测试点都 pass。copilot 在公开测试点的加持下，很轻松地立刻给我实现了所有的基础功能，甚至连脚本也不用写。

在此基础上我观察了一下代码的框架，想找到一些数据结构可以简化的地方，但很遗憾现在 AI 几乎不会写冗余的内容了，没有什么可以优化的部分。

### 3.2 Bonus 功能

公开测试点并没有涉及 Bonus 功能，因此我比较谨慎地让 copilot 在实现好以后写一些脚本自己评测一下，并且要求测试脚本包含的范围尽可能广一些，尽量覆盖到一些边界条件。

它写好以后虽然出现了一些“Failed”，不过后面自己迭代了几轮也都给改过来了，还很贴心地帮我“基础 + Bonus”全跑了一轮，确保所有都 pass 了才来向我交差。

我观察了一下它之前踩的坑，具体是这样的：

- **工具链/环境类问题**：比如 probe/fork_exit 这类 helper 如果没构建好，会导致一串看起来像 I/O 或协议错误的失败。Copilot 在最开始构建的时候沿用了基础功能的源代码，并没有进行相应的扩展，导致代码量激增且冗余，之后它发现需要整体优化重构后，整体的体量才变得正常。
- **时序/状态机语义**：detach/reattach 这种“断开期间还在跑”的，Copilot 刚开始并没有正确实现。于是遇到了一次 reattach 后 token 校验失败，它最终定位是“server 没有回放历史输出”后才把这个问题修复。

本来还不太放心这么快就实现的功能是不是真的能通过盲测，太过于边界化的脚本设计是不是会让它连比较普通的 Bonus 输入都通过不了，但从中期盲测的结果来看，我的担心似乎是完全多余的，过于优秀的模型实力让一切阻碍都变得不是阻碍。
