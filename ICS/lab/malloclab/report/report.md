## 一、glibc malloc 的演化历程

glibc 的 malloc 实现基于 ptmalloc 架构，其核心设计目标是在多线程环境下提供高效、可扩展的动态内存分配。从 2002 年至今，该分配器经历了若干次关键重构，每一次都针对特定场景下的性能瓶颈做出了改进。以下按照版本节点，梳理与性能直接相关的重要变更。

**glibc 2.3（2002）：arena 与 hook 分层定型。** 这一版本新增了 `malloc/arena.c` 和 `malloc/hooks.c`，将 arena 管理与分配逻辑分离，形成了清晰的层次结构。arena 机制允许多个线程在无竞争时各自持有独立的分配区域，从而降低了全局锁的争用频率。后续几乎所有并发优化和缓存优化都是在这一框架上展开的。

**glibc 2.25（2017）：tunables 框架。** tunables 提供了一套统一的调参入口，使得用户可以通过 `GLIBC_TUNABLES` 环境变量在运行时修改 malloc 的行为参数，而无需重新编译程序。从实验角度看，tunables 的价值在于它允许在同一版本内进行因果验证——通过在同一个 glibc 上开关某项特性，可以明确地将性能差异归因于该特性，而非版本间的其他混杂因素。

**glibc 2.26（2017）：tcache 引入。** 这是 glibc malloc 近十年最显著的性能改进。tcache 为每个线程维护一个本地空闲链表缓存。当线程需要分配小尺寸内存时，优先从本地缓存中获取，整个过程无需获取 arena 锁。被释放的小对象也会首先进入 tcache，同样避开了锁操作。这一设计将小对象分配释放的热路径从"全局同步"降为"线程本地"操作，预期在频繁分配释放小块的场景下产生数量级级别的加速。

**glibc 2.27（2018）：初始化序列优化。** 该版本改进了 malloc 的初始化顺序，减少了首次分配和多线程启动阶段的不必要开销。这个优化对长期运行的稳态吞吐影响不大，但在频繁创建和销毁线程、或者程序启动阶段有明显效果。

**glibc 2.31（2020）：mxfast tunable。** 该版本增加了 `glibc.malloc.mxfast` 可调参数，允许用户配置 fastbin 的最大块尺寸。fastbin 是一个使用 LIFO 单链表的快速分配路径，默认覆盖不超过 160 字节的 chunk。通过调大 mxfast，可以让更多中等尺寸的分配也走 fastbin 快速路径，在速度与碎片之间取得更灵活的折中。

**glibc 2.35（2022）：THP madvise 支持。** 为大块内存分配增加了 Transparent Huge Pages 支持，通过 `madvise` 请求内核使用 2MB 大页映射堆区域，从而降低 TLB miss 率。该优化仅在大工作集、大量页访问的场景下才能体现收益，且需要内核和系统策略的配合。

**glibc 2.42（2025）：tcache 大块缓存与热路径打磨。** 将 tcache 的适用上限提升至约 4MB，同时内联了 `tcache_free` 和 `tcache_try_malloc` 等关键函数，减少了热路径上的函数调用和分支。

上述演化中，tcache 的引入是一条清晰的分水岭：它将小对象分配从"每次都需要参与全局同步"变为"大多数时候只需本地操作"，这一变化带来的性能差异远大于其他各项优化的累积效果。我的核心目标就是用同一套基准测试在三组不同版本上量化这一差异，并观察 tcache 之后各版本在非纯热路径场景下的持续改进。

## 二、Benchmark 设计

### 2.1 版本选择与测试目标

实验选取了三组 Ubuntu 容器镜像，分别对应三组 glibc 版本：

- `ubuntu:16.04` → glibc **2.23**（tcache 引入前，作为基线）
- `ubuntu:18.04` → glibc **2.27**（tcache 已存在，且包含初始化优化）
- `ubuntu:20.04` → glibc **2.31**（tcache + mxfast tunable + 进一步整理）

这组选择覆盖了一条完整的性能演化链条：2.23 代表 tcache 之前的分配器状态，2.27 代表 tcache 引入后的首轮收益，2.31 代表在 tcache 基础上持续迭代后的状态。三者的间隔并非均匀——2.23 到 2.27 跨越了 tcache 这一决定性变更，而 2.27 到 2.31 则是更细微的改进期。基准测试的设计需要同时捕捉这两种不同量级的变化。


### 2.2 负载设计

仅靠单一尺寸、单一模式的分配无法刻画分配器的性能剖面。不同优化针对不同场景——tcache 对小对象热路径有效，fastbin 配置对中等尺寸有效，初始化优化对线程生命周期有效。因此测试程序设计了六类负载，每类负载分别对应一到多个优化点的敏感区域。

**small：单尺寸重复分配。** 以固定尺寸重复执行 malloc → 写入1字节 → free 的循环。这是最纯粹的分配器热路径测试，用于放大 tcache 的效果。伪代码如下：

```
for i in 0..iters:
    p = malloc(size)
    p[0] = (uint8_t)i
    free(p)
```

**sweep：多尺寸扫描。** 在 16B、32B、64B、128B、160B、256B、512B、1024B 八个尺寸上分别执行 small 负载。这组测试的目的是绘制"尺寸-延迟"曲线，观察不同版本在不同尺寸区间上的行为差异。前四个尺寸位于 fastbin 覆盖范围内，160B 恰好处在默认 mxfast 边界，256B 及以上则超出 fastbin 但仍可能落在 tcache 范围内。sweep 的实现逻辑如下：

```
sizes = [16, 32, 64, 128, 160, 256, 512, 1024]
for each sz in sizes:
    run small workload with size=sz, threads=1
```

**burst：批量分配释放。** 每轮连续分配 N 个相同尺寸的对象，写入后逆序释放。该模式模拟"阶段性批量操作"，会反复经历 tcache 的填充与排空。与 small 的差异在于，burst 每轮的额外开销包括指针数组维护和循环控制，这些成本与分配器本身无关，因此 tcache 的相对收益会被摊薄。伪代码如下：

```
for r in 0..rounds:
    for i in 0..burst_count:
        ptrs[i] = malloc(size)
        ptrs[i][0] = (uint8_t)(r + i)
    for i in burst_count..0:
        free(ptrs[i])
```

**mixed：多尺寸随机交错。** 每次分配时从 {16B, 32B, 64B, 128B, 256B} 中随机选取一个尺寸。与 sweep 的逐尺寸独立测试不同，mixed 在同一运行中频繁切换尺寸，这会打乱 tcache 的单一尺寸缓存优势，更接近实际应用程序中的分配模式。伪代码如下：

```
mix_sizes = [16, 32, 64, 128, 256]
for i in 0..iters:
    sz = mix_sizes[rand() % 5]
    p = malloc(sz)
    p[0] = (uint8_t)i
    free(p)
```

**thread_spawn：短生命周期线程。** 主线程依次创建 2000 个线程，每个线程执行 1000 次 malloc-write-free 后退出。该负载的核心测试对象是 malloc 的逐线程初始化路径。每个新线程的首次 malloc 调用会触发该线程的 arena 绑定和 tcache 初始化，创建与销毁的高频重复会放大多个版本在初始化序列上的差异。伪代码如下：

```
for i in 0..total_spawns:
    spawn thread:
        for j in 0..mallocs_per_thread:
            p = malloc(size)
            p[0] = (uint8_t)j
            free(p)
    join thread
```

**large_touch：大块内存触摸。** 分配 64MiB 内存，执行 memset 并逐页写入，然后释放。该负载的时间主要由物理内存访问和页表操作支配，分配器本身的开销占比极小。large_touch 在本次测试中扮演对照组角色——如果某一版本的该项数据出现显著波动，那更可能来自内核或编译器差异，而非 allocator 逻辑变化。

### 2.3 对照实验：tcache_off

对于 glibc 2.26 以上的版本，测试脚本额外执行一组 `GLIBC_TUNABLES=glibc.malloc.tcache_count=0` 的对照测试。关闭 tcache 后，如果性能显著回退，则可以确认之前观测到的提升确实由 tcache 驱动，而非版本间的其他差别——例如编译器版本不同、内核调度行为变化、或 allocator 中 tcache 之外的其他调整。

## 三、结果分析

### 3.1 单尺寸分配：tcache 的主战场

下表给出 small 负载（64B，2,000,000 次迭代）在三个版本上的 ns/op 值。ns/op 表示单次 malloc-free 循环的平均耗时，数值越低性能越好。

| 版本 | t=1 (ns/op) | t=8 (ns/op) | t=1 tcache_off (ns/op) |
|------|------------:|------------:|------------------------:|
| 2.23 | 27.68 | 3.46 | N/A |
| 2.27 | 3.17 | 0.54 | 19.04 |
| 2.31 | 3.54 | 0.78 | 19.89 |

从 2.23 到 2.27，单线程性能提升了 8.7 倍。这一跃升的幅度远超一般的"百分比优化"，说明热路径上发生了结构性的变化——arena 锁操作被替换为了线程本地指针操作。关闭 tcache 后，2.27 的延迟回升至 19.04 ns/op，该值虽然仍低于 2.23 的 27.68 ns/op，但差距已从 8.7 倍收缩为 1.45 倍。剩余的 1.45 倍差距可归因于 2.23 到 2.27 之间 arena 管理和 bin 操作等非 tcache 路径上的改进。

多线程场景下，版本间的差距同样显著。t=8 时 2.23 为 3.46 ns/op，2.27 为 0.54 ns/op，加速比约 6.4 倍。多线程加速比略低于单线程，原因是 t=8 的 ns/op 反映的是总体吞吐的倒数——八个线程并发执行时，arena 锁竞争在 2.23 上被八个线程分摊，使得单线程的劣势有所稀释。

关闭 tcache 后，2.27 和 2.31 在 t=8 下的表现为 2.68 和 2.66 ns/op，两者几乎一致且均优于 2.23 的 3.46 ns/op，说明除 tcache 以外的并发性能在 2.27 之后趋于稳定。

### 3.2 尺寸扫描：fastbin 边界与 tcache 覆盖范围

sweep 负载在八个尺寸上分别测量了 ns/op，构成了每个版本的尺寸-延迟剖面。下表列出了三个版本在基线配置（tcache 开启）下的完整数据。

**baseline（tcache 开启），t=1，单位 ns/op：**

| 版本 | 16B | 32B | 64B | 128B | 160B | 256B | 512B | 1024B |
|------|----:|----:|----:|-----:|-----:|-----:|-----:|------:|
| 2.23 | 27.26 | 27.44 | 26.89 | 26.24 | 26.58 | 26.39 | 26.53 | 26.42 |
| 2.27 | 3.22 | 3.17 | 3.24 | 3.18 | 3.16 | 3.19 | 3.21 | 3.23 |
| 2.31 | 3.45 | 3.74 | 3.51 | 3.67 | 3.48 | 3.49 | 3.48 | 3.55 |

2.23 在所有尺寸上的延迟几乎是一条水平线，约 26‒27 ns/op。这意味着在 tcache 出现之前，无论分配多大的对象，只要不触发 mmap，热路径成本大致恒定——每次都需要经过 arena 锁、bin 查找和链表操作。

2.27 和 2.31 在所有八个尺寸上都将延迟压低到了 3.1‒3.7 ns/op 的区间，同样是平坦的。这说明 tcache 对这八个尺寸提供了无差别的覆盖——从 16B 到 1024B 均落在 tcache 的默认缓存范围内，因此无论尺寸如何，命中的都是同一套线程本地缓存逻辑。

**tcache_off，t=1，单位 ns/op：**

| 版本 | 16B | 32B | 64B | 128B | 160B | 256B | 512B | 1024B |
|------|----:|----:|----:|-----:|-----:|-----:|-----:|------:|
| 2.27 | 19.31 | 19.09 | 19.09 | 24.30 | 24.43 | 24.12 | 24.16 | 24.34 |
| 2.31 | 19.97 | 19.84 | 19.80 | 24.68 | 24.55 | 24.70 | 24.49 | 24.50 |

关闭 tcache 后，剖面不再平坦，而是呈现出清晰的台阶结构：16B‒64B 约为 19‒20 ns/op，128B‒1024B 约为 24‒25 ns/op。台阶的位置恰好与默认 fastbin 边界吻合——在 64 位系统上，`MAX_FAST` 默认约为 160B，即 16B‒64B 的 chunk 可以走 fastbin 快速路径，而更大的 chunk 则需要进入常规 bin 的分配逻辑。这个台阶在 2.27 和 2.31 上高度一致，说明两个版本在 fastbin 和常规 bin 的基础路径上没有本质差异。

整体上，2.27 和 2.31 在 sweep 的带 tcache 配置下差异不超过 5%，属于同一性能档次。sweep 的核心价值在于揭示了两个层次的分化：tcache 带来的整体下移，以及 fastbin 边界在无 tcache 时的剖面台阶。

### 3.3 批量分配与随机尺寸

**burst，t=1，64B：**

| 版本 | baseline (ns/op) | tcache_off (ns/op) |
|------|-----------------:|--------------------:|
| 2.23 | 25.78 | N/A |
| 2.27 | 17.55 | 22.70 |
| 2.31 | 18.17 | 22.74 |

burst 的加速比约为 1.47 倍，远小于 small 的 8.7 倍。原因在于 burst 模式中每次迭代的额外操作——指针数组寻址、循环计数、倒序释放——这些操作独立于分配器的热路径，无论 tcache 开或关都需要执行。tcache 快的是 malloc 和 free 本身，但这两者在 burst 总耗时中的占比低于 small 模式。

关闭 tcache 后，2.27 和 2.31 的 burst 延迟几乎相同，且均接近 2.23 的水平，再次确认 burst 场景下 tcache 是性能差异的主要驱动，且 2.27 和 2.31 在非 tcache 路径上的 burst 逻辑基本等价。

**mixed，t=1 与 t=8：**

| 版本 | t=1 (ns/op) | t=8 (ns/op) | t=1 tcache_off (ns/op) |
|------|------------:|------------:|------------------------:|
| 2.23 | 37.55 | 5.11 | N/A |
| 2.27 | 5.14 | 0.76 | 32.18 |
| 2.31 | 5.69 | 0.75 | 30.74 |

mixed 负载在 t=1 下呈现出与 small 类似的 7.3 倍加速比，说明即便尺寸在随机变化，tcache 仍然能够有效命中——因为五个候选尺寸都落在 tcache 的覆盖范围内，各自对应不同的缓存槽位，互不干扰。

值得注意的数据点是 mixed tcache_off t=1：2.27 为 32.18 ns/op，2.31 为 30.74 ns/op。2.31 在这一项上比 2.27 快了约 4.5%。虽然幅度不大，但方向上是一致的——2.31 在处理尺寸频繁变化的负载时，非 tcache 路径的效率略有提升。这与 2.31 在 mxfast 和 bin 管理方面的持续整理有关。

### 3.4 线程生命周期压力

**thread_spawn，2000 次线程创建销毁，每次 1000 次 malloc-free：**

| 版本 | ns/op | tcache_off (ns/op) |
|------|------:|--------------------:|
| 2.23 | 83.27 | N/A |
| 2.27 | 57.42 | 74.43 |
| 2.31 | 59.17 | 67.04 |

在 tcache 开启时，2.27 比 2.23 快约 45%。这部分收益来自两个方面：每个线程内部的 1000 次 malloc-free 受益于 tcache，以及线程首次 malloc 时的初始化路径在 2.27 中得到了优化。

关闭 tcache 后，2.31 与 2.27 的差距变得明确：67.04 ns/op vs 74.43 ns/op，2.31 快了约 10%。thread_spawn 的 tcache_off 是本次测试中少数 2.31 明确优于 2.27 的场景。这个差异指向 malloc 初始化序列和线程绑定 arena 的路径在 2.31 中较 2.27 有可测的改进。

### 3.5 大块内存：对照组

**large_touch，64MiB，20 轮：**

| 版本 | ns/op |
|------|------:|
| 2.23 | 42,079,767 |
| 2.27 | 36,274,170 |
| 2.31 | 39,528,200 |

三个版本之间的差异不超过 16%，且不存在单调趋势。large_touch 的核心成本是 memset 写 64MiB 数据并逐页触发缺页处理，这部分时间完全由内存子系统和内核的缺页处理程序决定。分配器只在 malloc 和 free 两个瞬间参与，占总耗时的比例可忽略不计。因此 large_touch 的各项数据在整个测试中充当了环境噪声的参考基线——三个版本的该项数据越接近，说明容器之间的环境差异越小，其他负载上的差异越可以信任为分配器本身的变化所致。

## 四、 关键优化点的代码层面解释

**优化点一：tcache 对热路径的缩短（2.23 → 2.27）**

2.23 中，每次 malloc 的核心路径如下：

```
void *malloc(size_t bytes) {
    arena_get(ar_ptr, bytes);          // 获取 arena 锁
    victim = _int_malloc(ar_ptr, bytes);  // 在 bin 中查找/切割
    arena_put(ar_ptr);                 // 释放 arena 锁
    return victim;
}
```

无论分配多小的对象，都必须经过 lock → search bin → unlock 的完整流程。在高频场景下，lock 和 unlock 的原子操作本身，以及多线程竞争时引入的缓存一致性开销，构成了不可忽视的成本。

2.26 引入 tcache 后，路径变为：

```
void *malloc(size_t bytes) {
    idx = csize2tidx(bytes);                // 根据尺寸查 tcache 索引
    if (tcache != NULL && tcache->entries[idx] != NULL) {
        // 快速路径：从线程本地缓存取，无锁
        entry = tcache->entries[idx];
        tcache->entries[idx] = entry->next;
        return entry;
    }
    // 慢速路径：tcache 未命中，回退到 arena 逻辑
    arena_get(ar_ptr, bytes);
    victim = _int_malloc(ar_ptr, bytes);
    arena_put(ar_ptr);
    // 可选：从 arena 中额外取一批对象填充 tcache
    return victim;
}
```

快速路径仅包含一次索引计算、一次空指针判断和一次指针赋值，全部在栈上或线程本地存储中完成，不涉及任何同步原语。当分配模式使得大部分请求都能在快速路径中满足时，每操作耗时便从"数十纳秒的锁 + bin 操作"降低到"数纳秒的线程本地指针操作"。这就是 small 和 sweep 在 2.23 到 2.27 之间出现 7‒8 倍加速的根本原因。

**优化点二：mxfast 与初始化路径改进（2.27 → 2.31）**

2.31 新增的 `glibc.malloc.mxfast` tunable 使得 fastbin 的尺寸上限可以配置。在 2.27 中，fastbin 的覆盖范围由编译期常量 `MAX_FAST` 决定，约为 160B。2.31 将其改为运行时可通过 tunable 调整的值：

```
// 2.27：编译期固定
#define DEFAULT_MXFAST  (64 * SIZE_SZ / 4)

// 2.31：运行时由 tunable 控制
if ((unsigned long)(size) <= (unsigned long)(get_max_fast())) {
    // fastbin 快速路径
    fb = &fastbin(av, idx);
    victim = *fb;
    *fb = victim->fd;
    return victim;
}
```

在默认配置下，mxfast 的值在两个版本中相同，因此常规的 small 和 sweep 负载上没有明显差异。但 mxfast 的存在意味着用户可以根据具体应用的分配特征调整 fastbin 边界，在速度与碎片之间做出权衡——这一灵活性本身即是 2.31 相对于 2.27 的改进。

更可观测的差异体现在 thread_spawn 负载的 tcache_off 条件下。2.31 的 malloc 初始化序列对线程首次分配和 arena 绑定做了整理，减少了不必要的一致性与检查开销。thread_spawn 负载以 2000 次线程创建放大这一差异，最终在实测中体现为约 10% 的提升。这一改进的幅度虽远不及 tcache 引入的效果，但它体现了一种典型的软件演化模式：重大架构变更之后，持续的细节打磨同样在累积可测的收益。

## 五、回顾与总结

我与 AI 的协作从 glibc 的提交历史出发，一起梳理了 malloc 分配器从 arena 分层到 tcache 引入再到后续 tunable 扩展的完整演化链条。在此基础上，我们设计了一套覆盖单尺寸、多尺寸扫描、批量操作、随机尺寸交错和线程生命周期五类场景的基准测试，以三组 Ubuntu 容器镜像为载体，对 glibc 2.23、2.27 和 2.31 进行了系统的横向对比。

实验数据清晰地展示了 tcache 在 glibc 2.26 引入后带来的数量级级别性能提升：小对象单线程分配延迟降低了约 8.7 倍。关闭 tcache 后的对照实验确认了该提升的因果关系。多尺寸扫描揭示了 fastbin 边界在分配剖面中的台阶效应，而 thread_spawn 负载捕捉到了 2.27 到 2.31 之间初始化路径改进带来的温和但可测的收益。large_touch 对照组的三版本高度一致，验证了容器间环境差异未对主要结论构成混淆。

整个过程从阅读提交记录、设计评测方案、编写基准程序到分析数据和撰写报告，形成了一条完整的实验脉络。我最核心的收获是，系统软件的性能演化是由少数结构性变更主导，辅以大量渐进式打磨。这与 colab 的过程相似，在经过框架级别的调整后分数会跳跃式变化，之后更多的是参数微调，帮助小数点后一位甚至后两位进一步提升。
