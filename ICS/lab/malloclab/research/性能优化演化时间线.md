
# glibc malloc（ptmalloc）性能优化演化时间线（基于提交历史）

本文档的目标是为“Lab 3：用 AI 探索 glibc 内存分配器的演化历史”的第三步基准测试设计提供依据：

- 以 **glibc 版本号**为骨架（release tag：`glibc-X.YY`）
- 聚焦 **`malloc/` 目录**中与性能直接相关的变更
- 对每个关键节点给出**可复核的证据**（commit、文件、NEWS 条目）

仓库位置：`glibc-upstream/`（本 workspace 内）。

---

## 方法与可复核命令

为了避免“凭印象写演化史”，本文只采用可以在仓库中复现的事实：release tag、`malloc/` 目录下的提交历史、以及顶层 `NEWS` 中的版本说明。

你可以用下面这些命令自行复核本文结论（在 `glibc-upstream/` 目录中运行）：

```bash
# 1) 查看有哪些 glibc release tags
git tag --list 'glibc-*' | sort -V | tail

# 2) 只看某个版本区间内，malloc/ 目录发生了什么
git log --oneline glibc-2.25..glibc-2.26 -- malloc

# 3) 用关键字定位“首次引入”类优化（-S 会找出引入/删除某字符串的提交）
git log -S tcache --reverse --date=short --format='%H %ad %s' -- malloc | head

# 4) 把“提交”映射回最早包含它的 release tag
git tag --contains <commit> | grep '^glibc-' | head

# 5) 查看某个提交具体改了哪些文件
git show --stat --oneline <commit>
```

## 版本详解（按性能影响组织）

### glibc 2.3：arena/hook 分层出现（早期架构定型）

**为什么它重要**

- 这是 glibc malloc 进入“ptmalloc 风格、多 arena 组织”后，在源码结构上一次非常显著的整理与定型。
- 后续很多并发/缓存/调参类优化，本质都是在这个框架上迭代。

**可以复核的证据**

- 版本区间：`glibc-2.2..glibc-2.3`
- 观察到新增文件：`malloc/arena.c`、`malloc/hooks.c`
- 代表性提交：`fa8d436c87`（commit message 为 “Update.”，但 `git show --stat fa8d436c87` 显示它：
	- 新增 `malloc/arena.c`（~746 行）
	- 新增 `malloc/hooks.c`（~631 行）
	- 大幅改动 `malloc/malloc.c`（数千行规模）

**对性能的直觉影响（用于后续 benchmark 设计）**

- 多线程/多核下，arena 机制通常用于降低全局锁竞争；
- 在单线程小对象负载下，这个时期还没有 tcache 这类“线程本地热路径缓存”，性能差异更可能体现在 bin/合并策略等细节。

---

### glibc 2.25：Tunables 框架（为 malloc 调参铺路）

**为什么它重要**

- 从实验角度，tunables 的价值是：同一版本 glibc 下，你可以通过 `GLIBC_TUNABLES=...` 快速改变 malloc 行为，从而在报告里解释“为什么某个优化没体现/体现得不明显”。
- 从演化角度，tcache、mxfast、THP 等在实现上都需要一个可配置入口，tunables 框架让这些能力更系统化。

**证据**

- 提交：`67e58f3941`（Add framework for tunables）
- 最早包含 tag：`glibc-2.25`

---

### glibc 2.26：tcache（线程本地缓存）引入 —— 小对象性能分水岭

**核心优化点**

- 为常见小对象分配/释放引入 per-thread cache：
	- 命中缓存时，尽量避免拿 arena 锁、减少 bin 操作
	- 在“频繁 malloc/free 小块内存”的负载下通常能显著提速

**证据（提交 + 版本映射）**

- 提交：`d5c3fafc43`（2017-07-06，Add per-thread cache to malloc）
- `git tag --contains d5c3fafc43 | grep '^glibc-' | head` 的最早结果为 `glibc-2.26`
- `git show --stat d5c3fafc43` 可见主要改动集中在 `malloc/malloc.c`，并同步更新 tunables 列表与文档。

**性能预期与适合的 benchmark 场景**

- 适合：单线程或多线程“高频小对象”工作负载（例如：大量 16B~1KB 的短生命周期对象）
- 不一定明显：大对象（直接走 `mmap` 或不进 tcache 的路径）、或应用本身不是 allocator-bound 的场景

---

### glibc 2.27：malloc 初始化序列优化（整理型优化）

**核心点**

- 改进初始化顺序/路径，减少某些情况下的额外开销。

**证据**

- 提交：`3381be5cde`（Improve malloc initialization sequence）
- 最早包含 tag：`glibc-2.27`
- `git show --stat 3381be5cde` 显示主要改动在 `malloc/arena.c` 与 `malloc/malloc.c`

**性能预期**

- 更可能体现在“程序启动后前几次 malloc/free”、“多线程初始化阶段”这类微基准；
- 对长时间运行、稳态阶段的吞吐提升可能不如 tcache/THP 那样显著。

---

### glibc 2.31：`glibc.malloc.mxfast`（fastbin 上限可调）

**核心点**

- 增加 tunable：`glibc.malloc.mxfast`，使 fastbin 的阈值可配置。
- 这类优化属于“可调优”能力：不同应用对“速度 vs 碎片”偏好不同。

**证据**

- 提交：`c48d92b430`（Add glibc.malloc.mxfast tunable）
- 最早包含 tag：`glibc-2.31`

**实验价值**

- 你可以在报告里通过调参展示：同一版本 glibc 下，allocator 行为如何改变性能曲线（以及碎片/峰值内存）。

---

### glibc 2.32：Safe-Linking（fastbin/tcache 链表指针混淆）

**它与性能的关系**

- Safe-Linking 的出发点主要是安全（缓解利用），不是性能。
- 但它会改变 fastbin/tcache 链表指针的处理方式，因此：
	- 可能引入轻微指令开销
	- 也可能影响某些微基准的对比结果（需要在报告里解释）

**证据**

- 提交：`a1a486d70e`（Add Safe-Linking to fastbins and tcache）
- 最早包含 tag：`glibc-2.32`

---

### glibc 2.35：THP（Transparent Huge Pages）madvise 支持

**核心优化点**

- malloc 增加对 Transparent Huge Pages 的 `madvise` 支持：
	- 针对大堆/大块映射，尝试使用 THP 提升内存访问效率
	- 典型收益来自更少的 TLB miss（尤其是大工作集顺序/随机访问场景）

**证据（提交 + 文件范围）**

- 提交：
	- `5f6d8d97c6`（malloc: Add madvise support for Transparent Huge Pages）
	- `7478c9959a`（malloc: Add THP/madvise support for sbrk）
- 最早包含 tag：`glibc-2.35`
- `git show --stat 5f6d8d97c6` 可见新增了 `sysdeps/*/malloc-hugepages.c` 及相关头文件，并更新 `malloc/malloc.c`、tunables 列表和手册。

**做实验时的关键注意事项**

- THP 是否生效高度依赖内核与系统配置；如果你的 benchmark 看不出提升，优先检查：
	- 是否真的触发了大页（以及是否被系统策略禁止）
	- 你的访问模式是否能从更大页受益（纯分配/释放、但不怎么 touch 内存，可能看不出收益）

---

### glibc 2.42：大块 tcache + 热路径性能优化

**核心优化点**

1) **tcache 支持缓存更大的 chunk**

- 2.42 的 `NEWS` 明确提到：tcache 可以缓存大块（通过调大 `glibc.malloc.tcache_max`，上限 4194304），并且“小尺寸也显著更快”。
- 这意味着：在“中等大小（不一定算大对象）且高频”的分配场景中，tcache 的适用范围扩大。

2) **`__libc_malloc/__libc_calloc` 与 tcache 热路径的多处 micro-optimization**

- 例如：内联、热路径搬移、减少分支等。

**证据（NEWS + 提交）**

- `NEWS`：Version 2.42 的 Major new features 中有专门条目描述 tcache 大块缓存与性能提升。
- 代表性提交（均可用 `git show --stat <commit>` 查看）：
	- `cbfd798810`：malloc: add tcache support for large chunk caching
	- `b0897944cc`：malloc: Improve performance of __libc_malloc
	- `36189c76fb`：malloc: Improve performance of __libc_calloc
	- `393b1a6e50`：malloc: Inline tcache_free
	- `5d10174581`：malloc: Inline tcache_try_malloc
	- `1c9ac027a5`：malloc: move tcache_init out of hot tcache paths

**适合的 benchmark 场景**

- 在 2.26/2.27/2.31/2.32/2.35 等“历史节点”之外，如果你想把第三个版本选得更“新”，2.42 很适合：
	- 能体现“同样有 tcache，但更快/可覆盖更大范围”的演进
	- 也能体现“热路径持续打磨”的收益

## 给第三步 Benchmark 的直接建议（最小可用）

如果你只想覆盖 **3 个版本**来完成实验，并且希望每个版本差异都“有故事可讲”，可以优先考虑：

- **2.25 vs 2.26**：tcache 引入前后（小对象吞吐、锁竞争）
- **2.26 vs 2.35**：在已有 tcache 的基础上加入 THP 支持（更偏“触摸内存/大工作集”场景）
- **2.35 vs 2.42**：大块 tcache + 热路径优化（更偏“同类优化持续迭代”的量化）

选择 workload 时的对应关系：

- 小对象高频分配/释放：优先突出 2.26（tcache）的收益
- 大块分配 + 大工作集访问（touch 内存）：优先突出 2.35（THP）的收益
- 中等大小、高频、且希望比较“新版持续打磨”：可突出 2.42（大块 tcache + hotpath）
